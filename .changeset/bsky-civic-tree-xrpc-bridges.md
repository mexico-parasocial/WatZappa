Wire the community civic tree data plane to XRPC. `com.para.community.getCivicTree` was a hardcoded stub that always returned `{nodes: [], edges: []}`, so the PARA client's deliberation graph rendered empty forever; it now proxies `getParaCommunityCivicTreeGraph` and reshapes data-plane edges (`source`/`target`) into the `relationshipView` wire shape (`source_card_id`/`target_card_id`, plus `author_did`/`created_at`). The contribution review pipeline — `com.para.community.civicTree.{listContributions,submitContribution,voteContribution}` — had data-plane implementations but no XRPC bridge and failed with 501 at runtime; all three are now served, with `authorDid`/`voterDid` bound to the authenticated credential instead of the payload. `createRelationship` (connecting two cards with a `supports`/`opposes`/… edge) is implemented end-to-end for the first time: new `CreateParaCommunityCivicTreeRelationship` Connect RPC, idempotent insert keyed on the unique (source, target) pair, active-membership check, and an XRPC bridge. Expected Connect denials (not a member, self-vote, missing card, already decided) surface as 400-class `InvalidRequestError` instead of opaque 500s. Because the frozen legacy lexicon registry predates these procedures, their schema docs are installed from `src/api/com/para/community/civicTree/schemas.ts` and handlers register via `server.xrpc.method` (the same escape hatch as the post-subscription endpoints).

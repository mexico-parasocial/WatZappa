# Matrix bridge

- Bind a persisted firehose cursor to the PDS data generation. A mismatched or future cursor must fail clearly; never replay a bridge database against another local PDS.
- The cursor is a JS number. vlpds seqs (unix_micros × 256 + writer) exceed 2^53, so the bridge consumes the relay's renumbered stream and refuses a seq it cannot hold (`UnsafeFirehoseSeqError`, PG `safeInteger`); never round one. PG returns int8 (`COUNT`, `BIGINT`) as text: convert with `safeInteger`.

- Follow root testing skill. Run package scripts with the repo's Node 22; rebuild native SQLite dependencies after changing Node major versions.
- `pnpm test:postgres` runs the suite against SQLite and a disposable local PostgreSQL container. `pnpm smoke:appservice` creates and removes an isolated Synapse container. Never point these fixtures at deployed databases.
- `db.transaction` is for database-only work. Await all operations inside it; no network requests or live SSE notifications before commit. Ingestion uses `ingestMatrixEvents` for both appservice and polling; persisted event_log records are the delivery source of truth.
- `getFailedSyncs` must return the camelCase `SyncLogEntry` contract on both database drivers; raw snake_case rows silently disable role/revocation retry dispatch.
- Provisioning jobs use `getProvisioningRetryJobs` independently of the general retry limit; retry current source-bound PDS records even after five failures. Reuse an existing alias only after checking its operator creator, community marker, room type, encryption and parent. Publish room mappings only after all rooms exist.
- SSE must check room access at delivery, including explicit DID audiences. Unscoped events are denied. In-process notifications only wake the durable log drain.
- Never authorize from public linkedChat records. Never use an admin token as an appservice/device token. MAS requires native client authorization: the client runs the homeserver's authorization-code flow; the bridge only derives/ensures identity via `POST /api/matrix-identity` against a verified CD-M4 proof. See CLIENT_INTEGRATION.md.
- Never persist or reintroduce a DID↔MXID mapping (CD-M1/CD-M6): `identity-proof.ts` is the only key→MXID derivation, there is no forward lookup, and `user_matrix_map` is dropped at startup. Reverse attribution (`getDidForMxid`) resolves through minted device sessions only and stays out of API responses. Membership is pull-based: verified join via `POST /api/community-join` + `/_synapse/admin/v1/join/{id}`; role changes project through `applyMemberRoles`; removal deactivates minted sessions. Every verified interaction ends with `reconcileMemberAccess` (role catch-up + removal bans for the presented account), and MAS-native clients register via `POST /api/matrix-attest` — keep new proof-bearing endpoints on that pattern.
- Matrix DMs by consent (`routes/dm-requests.ts`) are the one sanctioned exception to the no-mapping rule: a pending `dm_requests` row holds the requester's MXID, proved with audience `dm.v1`, which is its consent to share it with that recipient. Listings never return an MXID; only the recipient's accept returns it, once, and blanks it (the row stays `accepted` so the requester can match the invite's encrypted `com.para.dm.intro { requestId, did }`). Decline, cancel and the TTL delete rows. Do not reuse it as a lookup or extend what it stores.
- Owner mutations remain disabled on the PDS-side generic membership endpoints. The bridge-side handover exists (CD-M6 `applyMemberRoles`), but record-level owner transfer still needs its dedicated protocol. Do not reintroduce ownerless-ID claiming.
- MXIDs use `MATRIX_SERVER_NAME` (the homeserver's own `server_name`), not the host of `MATRIX_HOMESERVER_URL`. They differ everywhere but production: dev reaches Synapse at `localhost`, compose at `synapse`, while the server names itself `matrix.para.social`. A mismatch mints users Synapse treats as foreign and refuses to act on.
- MAS owns native user creation. Identity probes must not pre-provision a Synapse account; a new MAS login requires the localpart to be available. The derived-user appservice namespace is nonexclusive so it can observe without blocking MAS. Appservice account/session creation (and bridge-minted pushers) require the explicit legacy-only `MATRIX_ALLOW_APPSERVICE_LOGIN` flag; legacy accounts are registered through the appservice with `inhibit_login: true`. Account display names are never set from DIDs.
- A community's key is its account's profile at-uri as the firehose reports it (`evt.uri`, `at://<did>/com.para.community.profile/self`, OD-9), and its room alias is the DID's identifier (`communityAlias`): every profile's rkey is `self`, so an rkey alias would make every community fight over one room. The bridge learns nothing about membership from a chain event but whom to re-check (`handleChainEvent`); the authority service decides. The founding event names the founder just before the profile is created, so provisioning remembers it (bounded); without it the community DID stands in until the first refresh. Chamber mode and the officials and deputies lists have no account equivalent, so every community is unicameral.
- `/_synapse/admin/v1/rooms/{id}/{invite,power_levels}` and `/_synapse/admin/v1/send_event` do not exist in Synapse; `members` and `/_synapse/admin/v1/join/{id}` do. `inviteUser`/`kickUser`/`setPowerLevel`/`banUser` therefore use the spec client API as the room-creator admin user; joins of other users go through `/_synapse/admin/v1/join/{id}` (`MatrixAdminClient.joinUser`). Verify an admin endpoint against a live homeserver before building on it.
- Start the local Matrix stack with `make matrix-up` (`scripts/matrix-stack.sh`), never a bare `docker compose` from an arbitrary directory: the compose file mounts config by relative path, so the wrong cwd silently creates empty mounts and boots a configless Synapse and MAS.
- Chat message reports (`POST /api/moderation-report` with `matrixEventId`) carry room, event and a reason from `MESSAGE_REPORT_REASONS` only. The bridge resolves the sender itself (`getEventSender` → `getDidForMxid`), rejects a client `reportedDid` that disagrees, never returns the resolved DID, and never stores message text (F4, D2 in PARA `docs/MATRIX-COMMUNITY-CHAT-IMPLEMENTATION.md`): moderators read the message in the room from their own client. The moderator queue (`GET /api/moderation-reports`, `listReports`) groups reports per message and returns `reporterCount`, never reporter DIDs or text; don't reintroduce raw `chat_moderation_events` rows in responses.
- `getSpaceForCommunity` must return the camelCase `CommunitySpaceMap` on both drivers (`tests/space-map.test.ts`); the raw Postgres row made `space.spaceId` and the chamber rooms undefined, so every projection and sanction built an empty room list.
- Sanctions are recorded per DID as `mute`/`ban`/`sanction_lifted` rows in `chat_moderation_events`, replayed by `effectiveSanction` from the full history (never a time window: a permanent ban must not age out). Enforce them at the projection choke point, not once at issue time: a ban refuses `verifiedJoin` (`SanctionedMemberError`, 403 `Sanctioned`) and is re-asserted by `reconcileMemberAccess`; a mute is part of the power-level computation (`withMute`), because every verified interaction rewrites power levels from roles and used to undo it. Moderators and owners cannot be sanctioned. `sanction-enforcement.ts` applies/lifts on known accounts and returns an `EnforcementResult`; routes must report it and never claim success on `partial`/`failed`. Timed sanctions are lifted by `liftExpiredSanctions` (60 s), recorded as lifted only after Matrix succeeded.
- Risk and sanction badges leave the server only to moderators and the member themself (`getMemberList` takes the viewer); the app hiding them is not the boundary. Reports count distinct reporters (`hasReportFrom`, distinct count in `computeBadges`); moderators close them with `report_dismissed` events. A sanction's reason is stored in `report_reason`, which no other non-report event uses.
- Room placement goes through `entitledRooms` in `matrix-projection.ts`, shared by the verified join and role projection. Moderators and owners are entitled to every room of the community (both chambers and the observer room) because they review reports in-room and an encrypted room cannot be decrypted before one joined; projection joins newly entitled rooms and kicks from rooms a role no longer covers.

- Resolve membership/roles only through `createAuthorityResolver` and the scoped
  AppView service credential. No creator or membership-record role fallback.
  Run initial authority reconciliation before serving and refresh at joins,
  authorization, SSE delivery, native interaction and retry; periodic reconciliation
  catches expiry/indexing lag. Verification failure suspends access and invokes
  device/room revocation; deployment requires both service revisions and the secret.

- Chat-off mode (`MATRIX_CHAT_ENABLED=false`, `chat-mode.ts`): `ctx.matrix` is null and the projection is `createChatDisabledProjection`. Governance reads chamber mode from the space-map row, so a community created then still gets one, holding `unprovisionedSpaceId` instead of a room id, plus a failed `create_space` sync entry that the retry worker provisions once chat is on. Anything that uses a space's room ids must check `isProvisionedSpace` first; new Matrix-only routes get `chat: true` in the router.
- `Firehose.start()` only returns when the consumer stops. In `bridge.ts`, schedule every periodic job before awaiting it; anything after it never runs (proposal transitions, badge and sanction sweeps were dead this way).
- Native device revocation (`MatrixAdminClient.adminDeactivateDevice` → `mas-admin.ts`) finishes every matching MAS OAuth/compat session before deleting the Synapse device; Synapse deletion alone leaves refresh tokens usable. Use the dedicated confidential MAS admin client on the private listener. Repeated revocation re-enforces authority even if a row already says revoked. Device attestation requires a live Synapse device for the proven MXID; fail closed on lookup errors.
- Chat operations (`ops.ts`) run on a separate, opt-in private listener, chat on only. Require both the trusted proxy credential and an independently allowed operator. Writes require the exact configured Origin, action header and a durable `chat_ops_audit` row (`control-store.ts`) before side effects. Job retries go through the sync_log provisioning queue, never a stored payload. Never return device DID/MXID pairs, tokens, message bodies or upstream error bodies.

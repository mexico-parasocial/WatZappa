# Matrix bridge

- Bind a persisted firehose cursor to the PDS data generation. A mismatched or future cursor must fail clearly; never replay a bridge database against another local PDS.

- Follow root testing skill. Run package scripts with the repo's Node 22; rebuild native SQLite dependencies after changing Node major versions.
- `pnpm test:postgres` runs the suite against SQLite and a disposable local PostgreSQL container. `pnpm smoke:appservice` creates and removes an isolated Synapse container. Never point these fixtures at deployed databases.
- `db.transaction` is for database-only work. Await all operations inside it; no network requests or live SSE notifications before commit. Ingestion uses `ingestMatrixEvents` for both appservice and polling; persisted event_log records are the delivery source of truth.
- `getFailedSyncs` must return the camelCase `SyncLogEntry` contract on both database drivers; raw snake_case rows silently disable role/revocation retry dispatch.
- PostgreSQL int8 counters and the rsky cursor arrive as strings. Convert bounded local values with checked safe-integer conversion; store the relay cursor as BIGINT. Never install a global int8-to-Number parser or convert VLPDS upstream cursors to JavaScript numbers.
- SSE must check room access at delivery, including explicit DID audiences. Unscoped events are denied. In-process notifications only wake the durable log drain.
- Never authorize from public linkedChat records. Never use an admin token as an appservice/device token. MAS requires native client authorization: the client runs the homeserver's authorization-code flow; the bridge only derives/ensures identity via `POST /api/matrix-identity` against a verified CD-M4 proof. See ../../docs/MATRIX_V2.md.
- Never persist or reintroduce a DID↔MXID mapping (CD-M1/CD-M6): `identity-proof.ts` is the only key→MXID derivation, there is no forward lookup, and `user_matrix_map` is dropped at startup. Reverse attribution (`getDidForMxid`) resolves through minted device sessions only and stays out of API responses. Membership is pull-based: verified join via `POST /api/community-join` + `/_synapse/admin/v1/join/{id}`; role changes project through `applyMemberRoles`; removal deactivates minted sessions. Every verified interaction ends with `reconcileMemberAccess` (role catch-up + removal bans for the presented account), and MAS-native clients register via `POST /api/matrix-attest` — keep new proof-bearing endpoints on that pattern.
- Owner mutations remain disabled on the PDS-side generic membership endpoints. The bridge-side handover exists (CD-M6 `applyMemberRoles`), but record-level owner transfer still needs its dedicated protocol. Do not reintroduce ownerless-ID claiming.
- MXIDs use `MATRIX_SERVER_NAME` (the homeserver's own `server_name`), not the host of `MATRIX_HOMESERVER_URL`. They differ everywhere but production: dev reaches Synapse at `localhost`, compose at `synapse`, while the server names itself `matrix.para.social`. A mismatch mints users Synapse treats as foreign and refuses to act on.
- MAS owns native user creation. Identity probes must not pre-provision a Synapse account; a new MAS login requires the localpart to be available. The derived-user appservice namespace is nonexclusive so it can observe without blocking MAS. Keep passwords/free registration disabled and force the trusted IdP subject as localpart. Appservice account/session creation requires the explicit legacy-only MATRIX_ALLOW_APPSERVICE_LOGIN flag. Never auto-adopt pre-existing appservice users into MAS without a reviewed migration. Account display names are never set from DIDs.
- A community's key is the board record's at-uri as the firehose reports it (`evt.uri`), and its room alias is the rkey. Never reconstruct the uri — `com.para.community.board` has no `slug` property, so a reconstruction files every community under `.../board/community`, which no membership record ever references and whose alias every community then fights over.
- `/_synapse/admin/v1/rooms/{id}/{invite,power_levels}` and `/_synapse/admin/v1/send_event` do not exist in Synapse; `members` and `/_synapse/admin/v1/join/{id}` do. `inviteUser`/`kickUser`/`setPowerLevel`/`banUser` therefore use the spec client API as the room-creator admin user; joins of other users go through `/_synapse/admin/v1/join/{id}` (`MatrixAdminClient.joinUser`). Verify an admin endpoint against a live homeserver before building on it.
- Start the local Matrix stack with `make matrix-up` (`scripts/matrix-stack.sh`), never a bare `docker compose` from an arbitrary directory: the compose file mounts config by relative path, so the wrong cwd silently creates empty mounts and boots a configless Synapse and MAS.
- Chat message reports (`POST /api/moderation-report` with `matrixEventId`) carry room, event and a reason from `MESSAGE_REPORT_REASONS` only. The bridge resolves the sender itself (`getEventSender` → `getDidForMxid`), rejects a client `reportedDid` that disagrees, never returns the resolved DID, and never stores message text (F4, D2 in PARA `docs/MATRIX-COMMUNITY-CHAT-IMPLEMENTATION.md`): moderators read the message in the room from their own client. The moderator queue (`GET /api/moderation-reports`, `listReports`) groups reports per message and returns `reporterCount`, never reporter DIDs or text; don't reintroduce raw `chat_moderation_events` rows in responses.
- Room placement goes through `entitledRooms` in `matrix-projection.ts`, shared by the verified join and role projection. Moderators and owners are entitled to every room of the community (both chambers and the observer room) because they review reports in-room and an encrypted room cannot be decrypted before one joined; projection joins newly entitled rooms and kicks from rooms a role no longer covers.

- Native device revocation must finish every matching OAuth/compat session in MAS before deleting the Synapse device; Synapse deletion alone leaves refresh tokens usable. Use the dedicated confidential MAS admin client on the private listener. Repeated revocation must re-enforce authority even if a legacy database row already says revoked.

- Community provisioning uses durable chat_provision_jobs before network calls. A claim has a bounded lease and attempt fencing; retries may create infrastructure, never restore old membership roles. Persist the complete room map in a database-only transaction. Legacy aliases require provenance/encryption review.
- Chat operations run on a separate, opt-in private listener. Require both the trusted proxy credential and an independently allowed operator; PDS admin unlock is insufficient. Writes require the exact configured Origin, action header and durable request-id audit before side effects. Never return device DID/MXID pairs, tokens, message bodies or upstream error bodies.

- Device attestation requires a live Synapse device for the proven local MXID. A valid identity proof plus an arbitrary device string is insufficient; fail closed on lookup errors and never persist a fabricated device.
